B-1 DERIVATIONS - WHAT WE HAVE AND HOW TO EXTEND
================================================

Taken from config/derivations.yaml, src/agents/derivation.py and
src/agents/database_derivation.py.

There are 8 derivation TYPES (D1 to D8). No other type is allowed: any other
`type` in derivations.yaml raises UnknownDerivationError.

derivations.yaml holds 15 INSTANCES of those types. An instance is one named
entry: a type plus its settings. Its name is its key in the extended record
(derived.values.<name>) and in B-1's tables.

D1 to D6 run once per run, so each gives a list, one entry per run, oldest
first. D7 and D8 look across runs and give one result.


1. THE 15 INSTANCES
-------------------

2. WHAT EACH TYPE DOES
----------------------

D1 threshold_compare
  Compares one sensor field against a fixed threshold, per checkpoint.
  Settings: source, scope ("checkpoints" or one checkpoint_id), field_path,
            threshold (a number), direction (above or below).
  Gives:    per checkpoint: value, exceeds, delta (value - threshold).
            Per run: exceeds_count, not_exceeds_count, inputs_used, inputs_excluded.
  Equal to the threshold does not exceed it.

D2 condition_count
  Counts items in a run that meet a named condition.
  Settings: scope (checkpoints, findings or sensor_alerts), condition (a name
            from `conditions:`).
  Gives:    count, matching_ids, population, inputs_excluded, excluded_items.
  Count-by-value form: set by_value (a field) and expected (a list of values)
            instead of condition. Gives one count per value. Expected values
            are always listed, with 0 if none. Any other value is listed as
            found, never merged into an expected one.

D3 proportion
  Share of items in a run that meet a named condition.
  Settings: scope, condition.
  Gives:    numerator, denominator, proportion, percentage, numerator_ids.
  NOT_COMPUTABLE when the denominator is 0.

D4 group_mean
  Mean of one sensor field per group, per run.
  Settings: field_path, source (checkpoints or samples),
            group_by (zone, run_id or kind).
  Gives:    per group: mean, n, inputs_excluded, inputs_stale.
            Per zone it also lists the zone's checkpoints.

D5 group_max
  Highest value of one sensor field per group, per run.
  Settings: same as D4.
  Gives:    per group: max, source_id, source_timestamp, tied_with (on a tie),
            n, inputs_excluded, inputs_stale.

D6 rank_top_n
  The n highest readings of one sensor field, per run.
  Settings: field_path, source, n.
  Gives:    ranking (rank, id, value), n_requested, n_returned, population.
  A reading tied with the last place is included, so n_returned can be more
  than n.

D7 run_set_difference
  Compares the two latest runs by checkpoint id only.
  Settings: none.
  Gives:    run_a (earlier), run_b (latest), only_in_a, only_in_b, in_both,
            and their counts. Says what differs, never better or worse.
  NOT_COMPUTABLE with fewer than two runs.

D8 run_date_range
  When the runs took place.
  Settings: none.
  Gives:    earliest, latest, span_days, run_count, runs_without_start,
            day_count, days_without_run, and each day with its runs.


3. ELIGIBILITY (WHAT GETS LEFT OUT BEFORE ANY DERIVATION)
---------------------------------------------------------

Eligibility runs first, once per field. Derivations only read its results.

Sensor fields (accelerometer.*, environment.*, particulate.*):
  - The checkpoint must be COMPLETED.
  - The device flag for that block must be true:
      adxl345_ok -> accelerometer
      bme680_ok  -> environment
      sps30_ok   -> particulate
  - The sensor must be connected, and the value must be recorded.
  - A sample is judged by its nearest checkpoint, and its own status must
    be connected.

Record fields (checkpoints.*, findings.*, sensor_alerts.*):
  - The field must be recorded.
  - For checkpoints, the checkpoint must be COMPLETED, except for fields in
    status_exempt_fields (now just `status`), so a MISSED checkpoint still
    counts when the question is about its status.

Everything left out is kept, with its reason, in derived.excluded and in
the rec_exclusions table.


4. THE TABLES B-1 QUERIES
-------------------------

All in output/b1_database.sqlite. Nothing in them is computed: every value is
copied from the records or the extended record. Most rows carry `path`, where
the value sits, so it can be cited.

The corpus and the runs
  corpus             1 row: run_count, first/latest/previous run_id, first/latest start_time
  runs               1 row per run: run_order, is_latest, is_previous, facility,
                     run_status, final_status, start/end time, duration, and the
                     counts the robot declared (total_required, completed, passed,
                     failed, missed, warned, finding_count)

What the runs recorded (no derivation)
  rec_checkpoints    1 row per checkpoint visit: id, name, zone, status,
                     result_status, timestamp, missed_reason, observed, notes, ...
  rec_findings       1 row per finding: finding_id, severity, status,
                     checkpoint_id, zone, feature, description, recommended_action
  rec_sensor_alerts  1 row per alert: code, severity, label, description,
                     nearest checkpoint, zone
  rec_events         1 row per event log entry
  rec_readings       1 row per eligible sensor reading and field
  rec_exclusions     1 row per scope, block and reason that eligibility left out

Derivation tables (one set per type; D1-D3, D7, D8 share a table across
instances, told apart by the `instance` column)
  D1  d1_threshold_compare, d1_checkpoints
  D2  d2_condition_count, d2_matching_ids, d2_by_value, d2_excluded_items
  D3  d3_proportion, d3_numerator_ids
  D4  d4_<instance>, d4_<instance>_checkpoints      (one pair per instance)
  D5  d5_<instance>, d5_<instance>_checkpoints      (one pair per instance)
  D6  d6_<instance>, d6_<instance>_ranking          (one pair per instance)
  D7  d7_run_set_difference, d7_checkpoints
  D8  d8_run_date_range, d8_days, d8_day_runs

The D4, D5 and D6 tables today:
  d4_group_mean_vibration_rms_g, d4_group_mean_temperature_c, d4_group_mean_pm2_5
  d5_group_max_vibration_rms_g,  d5_group_max_temperature_c,  d5_group_max_pm2_5
  d6_rank_top_n_vibration_rms_g, d6_rank_top_n_temperature_c, d6_rank_top_n_pm2_5
  each with its _checkpoints (D4, D5) or _ranking (D6) table.

6. HOW TO EXTEND
----------------

A. A new instance of an existing type: config only.
   Add an entry under `derivations:` in config/derivations.yaml.
   - Its table is made from config (D4, D5, D6 get their own tables).
   - The router offers it automatically and describes it from its settings.
   - A sensor field_path needs a `decimals` entry in config/report.yaml
     (all the sensor fields above already have one).
   - A new D2/D3 condition goes under `conditions:` first: one field and
     one exact value (case matters).
   Examples that need nothing else:
     group_mean of environment.humidity_pct per zone
     condition_count of sensor_alerts by_value severity
     condition_count of findings by_value feature

B. A new derivation TYPE: code, and allowed only if the brief allows it
   (it permits these eight). It would need all of:
   - the function in src/agents/derivation.py, added to DERIVATIONS (and
     PER_RUN if it runs per run)
   - its tables and an add_ function in src/agents/database_derivation.py
   - a route module in src/agents/routes/, added to PROMPTS

C. Do not add:
   - a type outside the eight
   - a condition written inline in a derivation (it must be named)
   - a sensor field_path without a decimals entry
   - a derivation that says better, worse, improved, fixed or caused:
     derivations state what the records hold, nothing more
