7. Row sign-off (Milestone 3). The calculation is in src/common/signoff.py, not src/query, because the report uses it and nothing may import from src/query. This is the same as could_not_read.

- The sign-off settings are the signoff block of config/report.yaml: the threshold, rows_dir, and each shortfall category with its meaning and the statuses it reads. config/signoff.yaml, which section 7 of the brief lists, was removed, so the threshold has one home and is covered by config_hash.
- Rows are defined per facility, one file each in config/signoff/<facility_id>.yaml. Each row lists its checkpoints and its expected_subjects. A facility with no file is not signed off. For now only sis_racks_checkpoint_route and sis_facility_checkpoint_route have files.
- One subject is one checkpoint. expected_subjects must equal the number of checkpoints listed, or the file is refused. Any other number would leave subjects that no shortfall category accounts for.
- expected_subjects are placeholders (the checkpoint count of each row) until the client sends the real counts.
- The racks rows follow the rack.row field in the record (rows A, B, C). The UPS is in row B, as the record files it. ac_1, ac_2 and dock_standoff are in no row. sis_facility has no racks, so checkpoint_1 to checkpoint_7 are one row and the dock is left out.
- ups_back is only on runs from 2026-08-18 onward. On earlier runs it counts as a missed checkpoint, so row B on those runs is at most 13/14.
- Each checkpoint is counted in exactly one place, the first that applies: missed (not in the run, or status is not COMPLETED, so PENDING and IN_PROGRESS count as missed), unresolved (no image is a readable file, or observed = no_evidence), unscoreable (no PASS, FAIL or WARN verdict), could_not_read, abstained (one of its own detections abstained), otherwise readable. So expected - readable always equals the shortfall total.
- could_not_read is checked before abstained. An abstained run-level finding is already a could_not_read entry, and counting it again would break the arithmetic.
- On the current data unscoreable and abstained are always 0: every completed checkpoint has a verdict, and detections are empty in every run. The rules are there so that a future run is not counted as readable when it is not.
- Confidence is rounded down to two places, so the figure shown is never higher than the real one. The threshold is checked against the figure shown, so the verdict always matches what the reader sees.
- signed_off_at is the report's generated_at, so the PDF, the manifest and the sign-off share one time.
- The manifest's row_signoff entries carry only the brief's keys. The list of what was not covered is only used for the report's wording.
- A checkpoint visited twice in one run is judged by its last visit.
- Open: config_hash covers report.yaml, so it covers the signoff block, but not the per-facility row files. A change to a row file does not change it.

Second-step routing check (Milestone 3). config/intents.yaml has routing.second_step_check. true: the second-step semantic router (src/router/second_step_derivation.yaml and second_step_lookup.yaml) must back each of the model's derivation or lookup picks at or above its minimum, or the question is unroutable. false: the picks go ahead unchecked, and nothing about the check is printed or put in the answer (no second_step_confidence key). 9. Comparison with the previous run (Milestone 4, section 3). It is built in src/compare/rounds.py and shown in the report and the manifest. The agent layer and its database are not changed.

- The previous run is found from the run folders, in src/common/runs.py. A run folder is named <YYYYMMDD_HHMMSS>-<facility_id>, so the folders beside this run's folder sort by time from their names. The previous run is the latest one whose time is before this run's. Only that run's record is read, at the same place inside its folder (records/run.json under data/, run.json under data_tenant/). In data/ every route's runs sit side by side, so only folders ending in this run's facility_id count.
- It is in src/common, not src/compare, because the seal chain has to name the same previous run, and src/seal may only import common. It does not read the seal chain: a seal hashes the report and manifest, so it is written after them.
- There is no previous run, and no comparison, when: this run's folder is not named after its run_id or has no time in it, no earlier run of the route is there, or the earlier run's record cannot be read. The run before it is never used instead. The reason is logged and printed in the report.
- The manifest has previous_run_id next to source_run_id, and a comparison array: one entry, or none when there is no previous run.
- The brief names the two runs round A and round B. The output says previous_run and current_run, and only_in_previous and only_in_current, in the manifest and the PDF. A and B read as code, not as a report.
- comparison_version is a config value (comparison.version in config/report.yaml), like the other versions, so config_hash covers it.
- The comparison is not optional. It has no switch in sections. It always renders, after the sensor alerts, and says why when there is no previous run.
- The attributions are their own closed set (Attribution in rounds.py), not gap types. A gap is something one run lacks. An attribution is about a difference between two runs.
- Checkpoints. A checkpoint in one run's checkpoints and not the other's is ROUTE_CHANGE. A checkpoint in both and reached (COMPLETED) in one only is MISSED, with the missed_reason of the run that missed it. If the other run's status is neither COMPLETED nor MISSED, it is UNATTRIBUTED: calling it missed would say more than the record does. Missed in both runs is not a difference and is not listed. in_both counts the checkpoints reached in both runs. A checkpoint id recorded twice is judged by its first entry.
- Sensors. The brief lists sensor availability as a dimension but its output shape has no key for it. The comparison adds "sensors", with only_in_previous and only_in_current, checked at the checkpoints reached in both runs. A block is not usable when the whole reading is not (the same rule as the SENSOR_UNAVAILABLE gap: no sensor block, ok=false, status not connected, or hub unreachable) or when its device flag is false (the SUBSYSTEM_OFFLINE gap). An absent flag claims nothing, so the block counts as usable, as it does for the gaps.
- The brief defines SENSOR_UNAVAILABLE as "absent because its device flag was false". The comparison also uses it when the whole reading was unusable. The records do say why in that case, so UNATTRIBUTED would be wrong. Each sensors entry has a reason that says which: for example sps30_ok=false, or the sensor hub was not reachable. The rule is reused from report.gaps, so a gap and a comparison entry can never disagree. The flags are read from the config passed in, not at module level.
- Readings (reading_changes). Checked in this order, and the first level where the two runs differ decides where it is reported: checkpoint reached in both (else Checkpoints), then sensor block usable in both (else Sensors), then the field values. So a block that is down is reported once, in sensors, and its fields are never compared. The brief also allows SENSOR_UNAVAILABLE on a reading, but here the block's entry stands in for its fields, and a placeholder value from an unusable block can never appear as a reading.
- All 12 numeric fields of the three blocks are compared. A value in both runs that differs is VALUE_CHANGED, with both values and difference = current minus previous. A value in one run and null in the other is UNATTRIBUTED, with difference null. Equal, or null in both, is not listed.
- Values are compared at the places they print to (decimals in config/report.yaml), and the difference is between the printed values, so a row never shows a difference of 0. previous and current are kept as recorded. A field with no decimals entry is compared as recorded. On the supplied runs no value differed only past the printed places, so this changes nothing today.
- difference_formatted always carries its sign: +0.610 or -1.580. difference stays a plain number.
- The brief's a and b are previous and current, as in the rest of the comparison.
- On the supplied runs almost every field differs between any two runs (a 42-checkpoint racks run gives 320 to 440 reading changes). The manifest keeps every one. The PDF prints them as one table per sensor block, a row per checkpoint and a column per field, each cell "previous → current" with the difference under it, and a dash where the two runs printed the same value. Nothing is ranked, filtered or left out: deciding which differences matter would be a judgement.
- Findings (finding_changes). Run-level findings are matched by their checkpoint_id and feature fields, as the brief says, not by finding_id: in the supplied runs the id's last part is not the feature (…:air_vents:airflow has feature blocked_airflow_path). Findings are independent of the checkpoint rules: every finding of both runs is compared, whether or not its checkpoint was reached in both. Severity and status are not compared.
- The brief's new, resolved and persisting are only_in_current, only_in_previous and in_both, the same names as the rest of the comparison. A finding only in the previous run is absent from the current one, not resolved: the records do not say it was fixed.
- Coverage (coverage_changes) is each run's figures over the whole run: evidence (how many evidence_images the checkpoints list, as a count), missed (checkpoints with status MISSED, as the reconciliation table counts them) and could_not_read (the same entries the report prints, so abstained findings only). The brief's output shape has evidence and could_not_read; missed is added because its section 3.2 table lists missed checkpoints under coverage. Keys are <figure>_previous and <figure>_current.
- Results (result_changes). Checkpoints COMPLETED in both runs whose result_status differs, with both results and UNATTRIBUTED: the records do not say why a result changed. A missed checkpoint's result (FAIL or PENDING in the supplied runs) is never compared: the robot did not reach it, so the result is not a verdict, and it is already reported as MISSED. The brief's a and b are previous and current.
- In the PDF, the checkpoints table lists every checkpoint on either route with each run's status and result side by side ("COMPLETED · FAIL", or "Not on route"). The sensors table gives each run's state of the block ("Usable", or the reason it was not) and the device. The findings table gives each run's severity and status and the finding's description. Rows where the runs differ are marked with a bar on the left. Which rows differ is read back off the comparison, so the page marks exactly what the manifest carries. The previous run's own values are read from its record, which is passed to the renderer for this.

10. Record continuity (Milestone 4, section 4). It is built in src/compare/continuity.py. It has its own command, record-continuity (python -m compare.cli data_tenant/<route>), and its own section in the report. The manifest does not carry it.

- The command is pointed at one route folder in data_tenant and reads every run folder in it. A run's date is the date in its folder name. The seals are read from output/sealed/<route>/<run_id>/ (--sealed to point elsewhere).
- The schedule is runs_per_day, under each tenant in config/tenants.yaml. It applies to every route the tenant lists. A route no tenant lists, or a runs_per_day that is not a whole number of 1 or more, is refused. Every tenant is set to 1 for now. scope.py reads only facility_ids, so the new key does not affect it.
- The window is --from and --to, both optional, both end days counted. One left out is the first or last run date in the folder. Only runs dated inside the window are counted.
- runs_expected is runs_per_day times the days in the window. runs_completed is the runs in the window that have a seal. A day with more sealed runs than the schedule counts them all, so continuity can be above 100%. runs_missing lists each day short of runs_per_day sealed runs, once for every run it is short; an extra run on one day does not fill a gap on another.
- coverage_mean is the mean, over the sealed runs, of each run's COMPLETED checkpoints out of all its checkpoints (computed_counts, not the record's own totals). A run with no checkpoints, or whose record cannot be read, counts as 0. It is null when there are no sealed runs, and continuity is then 0. continuity is worked out from the unrounded mean and rounded to 2 places.
- seals_verified and seals_broken come from verify_seal on each counted seal, against the record in data_tenant, with the route folder as the evidence root. INTACT is verified, TAMPERED is broken. COULD NOT VERIFY, or a seal that cannot be read, is neither; the report prints that count as "Could not verify". chain_intact is true only when there is at least one seal and every seal's chain check passed: a link that could not be checked is not claimed as intact.
- In the report, the window runs from the route's first run to this run's date, and only the runs before this one are counted. This run is sealed from its own report, so it has no seal when the report is made; counting it only when it happened to be sealed already would make the same run's report differ depending on when it was rendered. A run with no run before it, or not in the data_tenant layout, has no continuity, and the section says why.
- The section says continuity says nothing about condition, with the same kind of example as the row sign-off: a route where every scheduled run was sealed and every checkpoint failed has 100% continuity. Seals and the chain are printed beside the score as separate claims.
